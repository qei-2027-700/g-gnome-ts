# 小さな作業のエージェント引き継ぎ

一つの施設モデルなど、範囲と完成条件を短く指定できる作業を別のAIエージェントへ渡すための手順。依頼文はJSONファイルとして保存し、同じ内容をOrcaの作業者へ渡すか、別のエージェントに提示する。作業者の起動は依頼を実際に割り当てるときに行う。

## 渡すかどうかの判断

次の条件がすべて揃う作業を候補にする。

1. 対象を一施設・一機種などに限定でき、編集するファイルと触れない機能を指定できる。
2. 参考画像や仕様が作業者から実際に読める。別ワークツリーや別のマシンでは、元の作業場所に画像があるだけでは足りない。
3. 完了条件を画像比較、既存テスト、ゲーム内の確認として書ける。
4. 他の作業者と同じファイルを同時編集せず、未コミット変更を持つ作業場所を共有しない。
5. 原作で不明な形や機能を、作業者の推測だけで決める必要がない。

施設の例では、Scorpの地雷原制御施設の外観だけを作る作業は候補になる。任務進行や敵AIを同時に調整する作業、画像が渡せない作業、複数勢力の外観を一度に決める作業は、範囲を分けるか資料を揃えてから渡す。

## 依頼ファイル

[施設モデルの依頼例](agent-task-example.json)を複製し、`goal`、`inputs`、`editable`、`constraints`、`doneWhen`、`report`を対象に合わせて書く。`inputs`の各ファイルが作業者の環境にあるか、送る前に確認する。依頼例はまだ割り当てていない。

このリポジトリの `assets/reference/` はGit管理外であり、新しいワークツリーには画像が自動で入らない。今回追加した手順資料も未コミットの間は別ワークツリーにない。同じマシンの作業者には主作業ツリーの実ファイルを読める場所を示し、別のマシンの作業者には画像と資料を添付してから依頼する。

作業者には、原作で確認できる形と仮に補う形を分け、変更ファイル・実行した確認・スクリーンショット・残る差を報告してもらう。コミット、push、PR作成は依頼ファイルで明示した場合だけ行う。必要な画像がない、範囲外の仕様変更が必要、既存の未コミット変更と衝突する場合は、その時点で止めて理由を返してもらう。

## 渡し方と受け取り

Orcaで利用可能な作業者IDを確認したうえで、独立ワークツリーへ渡す場合は `orca orchestration worker-start --spec-file <依頼JSON> --worktree new-top-level --repo <repo-id> --name <作業名> --agent <作業者ID>` を使う。Orcaが対応するGrokモデルを選べる環境でも、作業者IDやモデルIDを推測して指定しない。Grok Botへ直接渡す場合は同じJSONと参照画像を提示する。いずれも、この文書を読んだだけでは作業者を起動しない。

報告を受けたら、指定した画像の視点で完成画面を照合し、変更範囲・テスト結果・未確認箇所を確認する。作業者の「完了」だけで採用を決めない。修正が必要なら差が分かる箇所を一つの追加依頼として返す。合格した変更だけを元の作業へ取り込む。
