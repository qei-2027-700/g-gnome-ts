# 判断モデルの利用検討：Clef・Jev

- 対象：G-Nome再現プロジェクトにおけるAI利用、とくに敵・味方の行動判断
- 状態：調査と試作案。採用・実装は未決定
- 調査日：2026-11-05
- 関連：[敵の行動](../gameplay/enemy-behavior.md)、[IFF・通信・仲間への命令](../gameplay/iff-and-communications.md)、[実装範囲](playable-1-1.md)、[実装計画](implementation-plan.md)

## 結論

ClefやJevは、限られた選択肢から行動を選ぶ用途に合う。G-Nomeでは、まず既存AIと同じ戦闘状態を入力する**開発用の比較実験**に使う。原作再現を優先する本編AIへの採用は、その結果と原作映像との照合を経て判断する。

最初の対象は、Merc Sentryの「接近・距離維持・側方移動・待機」という戦術判断が適している。ただし、この行動の一部は原作で未確認であり、試作の選択肢と原作仕様を混同しない。索敵、IFF、命令の受理、任務イベント、移動、照準、射撃可否、損傷、命中処理は既存のゲームロジックに残す。

## 製品の位置づけ

| 選択肢 | できること | この計画での位置づけ |
| --- | --- | --- |
| [Cloudflare Clef](https://developers.cloudflare.com/workers-ai/models/clef/) | 状態と型付きの質問から、選択肢・段階評価・真偽の確率を返す。Cloudflare上で提供され、[重みも公開](https://huggingface.co/Cloudflare/clef) | 戦術判断の比較候補。画像入力も可能だが、最初はゲーム状態を構造化して渡す |
| [Clef-flash](https://developers.cloudflare.com/workers-ai/models/clef-flash/) | Clef系の小型モデル | 応答時間と費用を重視する比較候補 |
| [Clef-omni](https://developers.cloudflare.com/workers-ai/models/clef-omni/) | テキスト・画像・音声・動画を入力できる判断モデル | 原作映像の場面分類などの調査候補。ゲーム中の戦術判断には入力形式が過剰 |
| [TypeSafe Jev](https://docs.typesafe.ai/introduction) | 状態と型付きの質問から判断結果を返す | Clefと同じケースで比較する候補 |
| 一般的な生成AI | 説明文・下書き・コード・画像などを生成する | 資料整理や素材の試作に利用。行動判断モデルとは別用途 |

ClefはJevのSystem One APIと互換性をうたう。ただし、実際の応答、確率の傾向、遅延、エラー、料金は同一とは限らない。モデル変更でゲーム体験が変わらないかは、同じ入力例で測る。[Cloudflareの発表](https://blog.cloudflare.com/clef-decision-models/)、[TypeSafeのAPI](https://docs.typesafe.ai/api/system-one)

## このプロジェクトでの用途と優先度

| 優先 | 用途 | 入力と出力 | 採用上の条件 |
| --- | --- | --- | --- |
| 1 | 敵機の戦術判断を比較 | 距離、射線、損傷、残弾、周囲の障害物など → 許可された行動候補 | 1-1の原作行動と比較し、原作にない退避などを本編へ混ぜない |
| 2 | 味方機の行動補助を比較 | 現在の命令、目標、射線、周囲の敵 → 命令の範囲内での移動方針 | Fキー命令、IFF、受理・完了条件を必ず優先する |
| 3 | 原作調査の補助 | 映像のフレームや観察メモ → 「巡回・発見・射撃」等の分類候補 | 時刻・映像・人による確認を残し、モデルの分類を原作の確定事実にしない |
| 4 | 制作資料の整理 | 文章や抽出済みの候補 → 未確認項目・確認優先度の分類 | 性能値や仕様をモデルに決めさせない |

会話文、ブリーフィング、台詞、機体画像を作る場合は生成AIの領域。ClefやJevは自由文や画像を生成しないため、この用途の主役にはならない。原作の台詞・外観を再現する場合は、生成結果を原作資料と個別に照合する。

## 試作する場合の境界

現在の敵AIは[`simulation.ts`](../../src/game/simulation/simulation.ts)で、ミッションの開始時刻、搭乗者、敵味方、誘引、索敵、視線、移動、射撃を処理する。味方への命令は同じシミュレーションと[`ally-orders.ts`](../../src/game/simulation/ally-orders.ts)に接続している。判断モデルを加えるなら、次の境界を守る。

1. シミュレーションから、モデルが判断に使える**観測済みの状態**だけを取り出す。敵が見えていないプレイヤー位置など、ゲーム内で知らない情報は渡さない。
2. コードがIFF、任務、命令、残弾、射線、機体状態から合法な選択肢を作る。モデルはその中から戦術方針だけを選ぶ。
3. モデルの返答を型・選択肢・対象ID・時点で検証する。古い返答、対象消失、無人化、IFF変更、通信失敗、タイムアウト時は既存AIへ戻す。
4. 移動・射撃・衝突・ダメージは既存のシミュレーションが実行する。モデルの返答を直接、座標やダメージ値にしない。

入力例は以下のように小さくする。値と行動候補は**実験用の例**であり、原作の確認済み仕様ではない。

```json
{
  "unit": "merc-sentry-1",
  "visibleTarget": true,
  "targetDistanceM": 90,
  "lineOfSight": true,
  "shieldFraction": 0.45,
  "missilesRemaining": 1,
  "currentOrder": "none",
  "allowedActions": ["approach", "hold", "strafe"]
}
```

`choice`の質問は「この状態で次の短い区間に取る行動を、許可された候補から一つ選ぶ」のように限定する。`score`で脅威度を求めてもよいが、原作にない行動を自動的に解禁する理由には使わない。確率やconfidenceは正解の保証ではないため、閾値を固定してからケースごとに誤りを調べる。[TypeSafeの質問形式](https://docs.typesafe.ai/primitives)、[confidenceの説明](https://docs.typesafe.ai/confidence)

## 実行方式

このゲームは現在、静的配信のブラウザゲームを基本としている。Cloudflare上のClefやJevをプレイ中に呼ぶなら、ブラウザに秘密鍵を埋め込まず、鍵を保持するサーバー側の中継が要る。通信の遅延・失敗・利用量制限を加味し、毎フレームの判断には使わず、数秒単位の方針更新などに限定する。ここでの更新間隔は設計案で、実測値ではない。

| 方式 | 利点 | 制約 |
| --- | --- | --- |
| 開発時だけAPIを呼び、結果を記録 | 本番の配信構成を変えずに比較できる | プレイ中の動的判断は試せない |
| Cloudflare WorkerからClefを呼ぶ | Cloudflare Pagesとの組み合わせを検討しやすい | サーバー側のコード、鍵・費用・障害対応が増える |
| Jevをサーバー側から呼ぶ | 同じ入力例でClefと比較できる | 外部サービスへの接続と鍵の管理が要る |
| Clefの重みを自前で実行 | API依存を減らせる可能性がある | 27Bモデルの実行環境と運用が必要。ブラウザへの同梱を前提にしない |

**現段階の推奨は開発時だけのAPI比較。** 本番への組み込みは、その比較で原作再現やプレイ体験の改善が確認できた場合に検討する。なお、CloudflareのAI Gatewayは推論モデルではなく、モデル呼び出しを管理する仕組みである。[Cloudflare AI Gateway](https://developers.cloudflare.com/ai-gateway/)

## 比較実験と採用基準

1. 1-1から10～20場面を採る。開始時の待機、接近による発見、遮蔽物、被弾後、IFF変更、目標の無人化・破壊、弾切れを含める。場面数は試験計画上の目安であり、原作資料が足りなければ増減する。
2. 各場面の観測状態、合法な行動、既存AIの行動、原作映像で確認できる行動を保存する。原作で確認できない場面には正解ラベルを付けない。
3. 同一の入力をClef・Clef-flash・Jevへ送り、選択、確率、応答時間、エラー、使用量を記録する。繰り返し実行し、選択の揺れも確認する。
4. 合法性違反、IFFや命令との衝突、原作観察との不一致を人が確認する。次に、同じ場面を実ブラウザで操作し、移動・射撃・任務進行への影響を見る。
5. 原作に近い行動が安定して選ばれ、失敗時に既存AIへ戻せる場合だけ、限定的な導入を検討する。改善が見られなければ既存AIを維持する。

指標は「原作で確認できた場面との一致数」「違法な行動の採用数（目標0）」「命令違反数（目標0）」「応答時間の分布」「API失敗時の継続可否」「1プレイ当たりの推定費用」とする。AI同士の勝率だけでは原作再現の良し悪しを判断できない。

Cloudflareの[2026-10-09の料金表](https://developers.cloudflare.com/changelog/post/2026-10-09-clef-omni-workers-ai/)では、入力100万トークン当たりClef-flashは$0.038、Clefは$0.240、Clef-omniは$0.150。料金や制限は変更されるため、実施時に[最新の料金表](https://developers.cloudflare.com/workers-ai/platform/pricing/)を確認する。単価だけでなく、1回の入力長、判断回数、Worker等の費用を合わせて見積もる。

## 無料枠と実行場所

[Cloudflare Workers AIの料金表](https://developers.cloudflare.com/workers-ai/platform/pricing/)を2026-11-05に確認した時点では、Free・Paidの両プランに**1日合計10,000 Neurons**の無料枠がある。Clef系もこの枠を使い、枠はアカウント内のWorkers AI利用で共有する。Freeプランでは枠を超えた呼び出しは失敗し、Paidプランでは超過分が課金される。Clef-flashは入力100万トークン当たり3,455 Neurons、Clefは21,818 Neurons。単純換算では、ほかのモデルを使わなければ無料枠はそれぞれ約289万・約46万入力トークンに相当する。実際の呼び出し回数は質問文を含む入力長で決まる。無料枠・料金は試す時点で再確認する。

使う場所は目的で分ける。

| 場所 | 役割 | このプロジェクトでの判断 |
| --- | --- | --- |
| 開発者のローカル環境 | 保存した戦闘場面をClefへ送り、結果を既存AIやJevと比較する | **最初の試作場所**。本番ゲームとCIを変えずに評価できる |
| GitHub Actions CI | コードの型チェックと自動テストを実行する | 既存の[CI設定](../../.github/workflows/ci.yml)はこの役割。モデルの実応答に依存するテストは通常のpush・PRチェックへ入れない。応答の揺れ、通信障害、無料枠の共有が合否を不安定にする |
| Cloudflare Worker | 公開ゲームからの判断依頼を受け、Workers AIのClefへ送る | プレイ中に使うと決めた場合の候補。ブラウザから鍵を直接渡さず、入力制限・応答検証・失敗時の既存AIへの復帰を設ける |

CIで確認できるのは、モデルへ送る状態の作成、合法な選択肢の列挙、返答の検証、失敗時の復帰など、**コード側の決定的な処理**。Clefの実応答の品質は、保存した場面を使う手動の比較実験で評価する。後に自動計測が必要になれば、通常のCIとは別の手動起動ジョブに分け、利用量と結果を記録する。

## 未決定事項

- ゲーム中の動的判断を本当に必要とするか。既存の条件分岐を調整した方が原作に近い可能性もある。
- プレイヤー向けの「AI実験モード」を設けるか、開発用の検証だけに留めるか。

この資料は採用判断のための調査であり、ゲームの仕様変更や実装済み機能を示すものではない。
