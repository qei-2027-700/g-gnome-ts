# G-Nome再現の実装計画

- 作品：G-Nome（1997年のPCゲーム）の再現
- 媒体：PC向けブラウザゲームを推奨
- 対象：技術構成、原作調査、ゲーム基盤、4勢力、キャンペーン制作
- 状態：Babylon.js・TypeScript・Viteを採用。製品版1-1から実装する方針。実装未着手
- 記録日：2026-10-22
- 関連：[企画・参考ページ](../../README.md)

## 推奨する構成と対象範囲

Babylon.js・TypeScript・Viteの採用はユーザー指定。最初はシングルプレイを対象とするフロントエンドとして作る案とし、戦闘、敵AI、ミッション進行、セーブ処理をブラウザ内で実行する。シングルプレイ限定は未確定。

20以上のミッションを見据えて共通基盤を設計する。正確なミッション総数と訓練の扱いを調査したうえで、収録対象の一覧を作る。最小デモの完成を全編再現の完了とは扱わない。

初期対象はキーボードとマウスを備えたPC。モバイル対応、オンライン対戦、アカウント、クラウドセーブは初期計画に含めず、希望があれば範囲を見直す。原作の操作・挙動を記録し、操作の現代化やバランス変更は別の判断として扱う。

## フロントエンドだけで十分か

シングルプレイの再現には、原則として十分。ミッション数や勢力数が増えても、それだけでバックエンドが必要になるわけではない。素材容量、読み込み時間、描画負荷は別途管理する。

| 機能 | 推奨する実行・保存場所 |
| --- | --- |
| 描画、入力、物理判定、敵AI、戦闘 | ブラウザ内 |
| 機体・武器・勢力・ミッション定義 | 配信する静的データ |
| モデル、テクスチャ、音声 | 静的配信。共通素材とミッション固有素材を必要時に読み込む |
| キー設定、音量、画面設定 | localStorageなどのブラウザ内ストレージ |
| キャンペーン進行、アンロック、セーブデータ | IndexedDB。ファイルへの書き出し・読み込みも用意する |

公開時にはHTML・JavaScript・素材を配る静的ホスティングが必要だが、ゲーム専用APIやサーバー側データベースは不要。開発用のNode.jsやViteは制作ツールであり、本番のゲーム処理用バックエンドではない。[Viteの静的配信資料](https://vite.dev/guide/static-deploy.html)

制作中は開発サーバー、配布時はビルド済みの`dist/`を使う。[ビルド・配布・プレイ環境](build-and-distribution.md)に手順案を記録する。現在はコマンドと配布物をまだ作成していない。

ブラウザ内データはユーザー操作やブラウザの保存領域管理で失われる場合があるため、セーブの書き出しを用意する。端末間同期は自動では行わない。[MDNの保存容量・削除条件](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)

将来、アカウント・クラウド同期・共有ランキングを追加する場合はバックエンドを検討する。オンライン対戦を追加する場合は、接続仲介や中継、状態同期、勝敗の管理を別途設計する。

## 4勢力の扱い

機体別の最高速度・防御・武装と武器の数値は、[機体性能・武器仕様の調査](../reference/vehicles-and-weapons.md)を参照する。公開資料で確認した暫定値と原作での検証結果を区別し、機体・武器・搭載装備・ミッションごとの装備差を別々に管理する。最初の再現対象は[製品版1-1](../missions/mission-1-1.md)。Union SentryでMerc Sentry・Merc Tactical Defenseと交戦する。

公開資料で確認できた勢力は以下の4つ。名称の確認元は [G-Nome Wikiの勢力一覧](https://g-nome.fandom.com/wiki/G-Nome_Wiki)、人類を含む4種族の説明は [MobyGames](https://www.mobygames.com/game/2850/g-nome/) を参照。正式名称、表記、性能差の確定には原作マニュアル・実機での確認が必要。

| 勢力 | 計画上のID案 | 現時点の確認状況 |
| --- | --- | --- |
| Union（人類側） | `union` | 名称・人類側であることを公開資料で確認 |
| Darken | `darken` | 勢力名を公開資料で確認 |
| Merc | `merc` | 勢力名を公開資料で確認。資料によってMercs表記もある |
| Scorp | `scorp` | 勢力名を公開資料で確認 |

4勢力を機体の色違いだけで表現せず、各勢力の機体、武装、外観、HUD、施設と、それぞれの差分を調査する。差分が存在するか、何が共通かを原作に基づいて整理し、未知の数値を補わない。

勢力と、そのミッションでの敵味方を分けて管理する。人物の所属、機体の所属、現在の搭乗者、相手からの識別状態を別の情報として持ち、機体を奪った後の判定を検証できる構成にする。4勢力が常時すべて敵対するとは決めつけない。

## 採用する技術構成

| 用途 | 採用案・判断方針 |
| --- | --- |
| 言語・開発 | TypeScript、Vite、pnpm。実装開始時に互換性を確認し、バージョンを固定する |
| 3D描画 | Babylon.jsを採用。最初はWebGLで基準環境を揃える |
| 当たり判定・地形追従 | Babylon.jsの衝突判定とHavok連携を候補に、坂・壁・乗降で方式を検証する。物理方式は未確定 |
| HUD・メニュー | HTML/CSS。毎フレーム変わる戦闘状態はゲーム側で管理する |
| データ | JSONとTypeScriptの型・実行時検証。ミッション定義はゲーム処理から分離する |
| 音 | Babylon.jsの音声機能またはWeb Audio。BGM・効果音・台詞の再生を管理し、開始操作後に音声を有効化する |
| 検証 | ゲーム状態の自動テストと、実ブラウザでの操作確認 |

コードとデータファイルを中心に管理し、ローカルで編集・ビルド・検証できる構成にする。操縦感、戦闘、AI、乗降、ミッション進行は独自実装する。[Babylon.jsの機能](https://www.babylonjs.com/specifications/)と[Viteでの開発](https://doc.babylonjs.com/guidedLearning/usingVite)を参照。

## ゲーム基盤の分け方

徒歩・操縦者・同乗者・施設内・脱出中・死亡を分ける。[歩兵仕様](../gameplay/infantry.md)に、人物と機体を分離した乗降・被弾・武器・施設の設計を記録する。1-1はUnion歩兵の徒歩開始から搭乗までを含める。

描画とゲーム状態を分け、一定間隔で移動・戦闘・AI・イベントを更新する。描画フレーム数が変わっても、移動速度や射撃間隔が大きく変化しない構成にする。

| 領域 | 責務 |
| --- | --- |
| 実行基盤 | ゲームループ、入力、開始・ポーズ・再開、素材の読み込みと解放 |
| ゲーム処理 | 徒歩・搭乗、操縦、武器、損傷、AI、識別、施設操作 |
| 表示 | 地形・機体・エフェクト、カメラ、HUD、音 |
| コンテンツ | 勢力、機体、武器、マップ、ミッション、キャンペーン順序 |
| 保存 | 設定、進行、セーブ形式のバージョン、書き出し・読み込み |

ミッション定義には安定したID、参照するマップ、登場ユニットと所属、目標、イベント、成功・失敗条件を持たせる。目標は単なる文章ではなく、撃破・到達・施設操作などの状態から判定する。イベントは一度だけ実行するか、繰り返すかを定義する。

共通部品で表現できないミッション固有処理は、そのミッション専用モジュールに置く。すべてのミッションを無理に同じ条件式へ押し込めない。

現在のコード配置は以下。テストは実装と同じフォルダに置く。

## 実装の順序と完了条件

### 1. 原作仕様を整理する

ミッション一覧と4勢力の機体一覧を作る。各情報には出典と確認状態を添える。原作マニュアル、操作映像、実機を使い、入力、操縦、武装、降機・強制排出・乗っ取り、識別、味方への命令、施設、損傷、セーブ仕様を調べる。映像や二次資料だけで分からない部分は未確認として残す。

完了条件は、キャンペーンの順序と対象数が整理され、最初に再現する原作ミッションについて開始条件・必要機能・成功条件・失敗条件が説明できること。全編の未調査部分は一覧で追跡する。原作資料が不足しても、調査と独立した技術検証は進められる。

### 2. 操縦・戦闘・乗り換えを検証する

初回の機体構成は製品版1-1に合わせる。プレイヤーはUnion Sentry、敵はMerc SentryとMerc Tactical Defense。[設定画面](../gameplay/settings.md)も初回の実装範囲に含め、難易度3段階・初期値Easyを用意する。仮地形・仮配置・仮パラメータは原作と照合済みのものから区別する。

仮モデルと小さな地形を使い、徒歩、自機の操縦、照準、射撃、被弾、敵の索敵・攻撃、降機、敵パイロットの排出、空いた機体への搭乗を作る。HUDには体力、機体状態、弾数、照準を表示する。4勢力のIDと機体・搭乗者の所属管理はこの段階から導入する。

敵AIの確定状況と調査手順は[敵の行動仕様](../gameplay/enemy-behavior.md)を参照する。仮AIでの技術検証と、原作Easyの1-1を照合した行動実装を区別する。

[上半身・砲塔の旋回](../gameplay/vehicle-articulation.md)は車体と分ける。360度回転・角度制限・固定を機体定義に持たせ、操縦、AI、モデル、カメラ、射線へ共通して反映する。

完了条件は、徒歩から搭乗し、敵と交戦し、降機して別機体に乗り換える一連の操作が成立すること。壁抜け、地面落下、乗降後に操作対象が二重に残る問題を解消する。乗り換え後の敵味方判定は、確認できた原作仕様に照らして検証する。

### 3. 原作ミッションを1本通して遊べるようにする

最初の対象は製品版1-1「Renegade Mercs」。Darken国境へ向かう途中でMerc軍と交戦する。このミッションのマップ、配置、目標、会話・通知、施設、イベントを実装する。必要に応じて味方AIや命令を追加する。開始画面から出撃し、成功または失敗に至り、再挑戦できる流れを作る。

完了条件は、原作に沿った開始から終了までを通して確認できること。達成順序が複数ある場合はそれぞれ検証し、原作との差分を記録する。基本部品のデモではなく、この段階を最初のプレイ可能版とする。

### 4. 全編を制作するための共通機能を揃える

残りのミッションが必要とする機能を一覧化し、4勢力の機体・武器、損傷、識別、施設、味方AI、地形の種類を順に追加する。性能や挙動の差は出典に基づくデータとして定義し、固有機能が必要なものは個別の処理を用意する。

あわせて、ミッションを直接起動する開発用画面、配置と当たり判定の可視化、イベント履歴、定義ファイルの検証を整備する。専用のGUIエディターは、データ編集だけでは制作が滞ると分かった場合に検討する。

完了条件は、各ミッションの必要機能と実装済み機能の対応が追え、機体・武器・イベントなどの参照ミスを検出できること。異なる必要機能を持つ複数の原作ミッションで共通処理を確認する。

### 5. キャンペーンを完成させる

調査済みの順序でミッションを追加し、それぞれを開始から終了まで検証する。進行保存、ミッション解放、ブリーフィング、結果表示、音、演出、操作設定を仕上げる。原作のミッション途中セーブ仕様を調べ、再現するか追加機能にするかを決める。途中セーブを採用する場合は、AI・弾・目標・イベント状態も復元対象にする。

完了条件は、合意した収録範囲の全ミッションを順番に進行でき、再起動後も進行を復元できること。未再現部分と意図的な変更を一覧にし、対象PC・ブラウザで通し確認を終える。

## 検証方針

状態遷移の自動テストは、乗降・死亡・機体破壊、弾数と発射間隔、勢力と識別、目標の達成順序、イベントの重複実行、セーブ復元に絞って意味のある条件を検証する。

実ブラウザでは、マウスの視点操作、フォーカスを失ったときの入力解除とポーズ、音声開始、地形・橋・施設との接触、各ミッションの成功・失敗・再挑戦を操作して確認する。検証結果と必要な画面記録は `docs/verification/` に残す。

性能は、段階2で基準PC・画面サイズ・ブラウザを記録し、60fpsを暫定目標として計測する。段階4以降は敵と弾が多い場面、ミッション切り替え後のメモリ解放、素材の読み込みを確認する。全ミッション分の素材を一括でメモリに載せない。

## 設定とBGM

[人物一覧](../story/characters.md)に従って、主人公ガンツと仲間の本編登場、会話出演、通信相手を分ける。[IFF・通信](../gameplay/iff-and-communications.md)は、4桁の識別、AIとレーダー、仲間への命令、任務イベントを接続する。Fキー通信は宛先選択と命令選択の2段階とし、Fキー不要の画面操作も用意する。

コックピットの共通機能は[HUD仕様](../gameplay/cockpit-hud.md)、Bの任務表示とSのウェイポイント選択は[任務地図・ウェイポイント](../gameplay/mission-map-and-waypoints.md)に従う。機体別の画面配置と原作マップの照合は未完了。

Windows・macOS双方を対象に、テンキーレスでも完結する[キー設定](keybindings.md)を用意する。原作キーとWeb版の共通プリセット案を分け、OS・ブラウザの予約操作、IME、フォーカス喪失を考慮する。全速出力を指示した際の女性音声も実装対象とする。

[武器の分類・表示とミサイル専用ビュー](../gameplay/weapons-and-missile-camera.md)を考慮する。レーザー・マシンガン・ミサイル・ミーゾン系の表示と消費資源を分離し、カメラ誘導ミサイルは操作と視点の一時切り替えとして実装する。3-3の武器は同資料の確認事項とし、1-1に追加しない。

日本語版の女性の確認音声と、確認後のYによるミッション中断を実装する。[中断と音の制作方針](../audio/mission-controls-and-audio.md)に未確認のキー・戻り先と、自作SEの扱いを記録する。

プレイヤーの搭乗成功時には、女性音声で搭乗先の機体名を1回読み上げる。機体ごとの名前・読み・音声を定義し、1-1のUnion Sentryへの搭乗時から対応する。乗り換え・再搭乗にも対応し、同資料に再生条件を記録する。

日本語版の女性案内は若い印象と厳粛な印象の2種類があるとのユーザー説明を記録し、対象・案内イベント別に声種を指定する。Darken Sentryと地雷原コントロール設備は厳粛な声。言語と声種を分け、日本語を先行し、後から英語の表示・字幕・音声を追加できる構造にする。英語版の声種の対応は未確認として扱う。

シールド低下・重大損傷の女性警告も同じ案内基盤で再生する。ユーザーの記憶にある台詞と、未確認の閾値・発声条件を区別し、シールド・エネルギー・部位損傷から別々の警告イベントを判定する。

カメラは機内・外部斜め・外部真後ろの3種類を実装する。機内表示は機体ごとに持たせ、乗り換え時に対応するコックピットへ切り替える。[カメラとコックピット](../gameplay/cameras-and-cockpits.md)に仕様と未確認事項を記録する。

難易度はEasy・Medium・Hardの3段階で初期値はEasy。[設定仕様](../gameplay/settings.md)に、設定画面・保存・反映タイミングと難易度別パラメータの扱いを定義する。原作の機体性能、ミッション固有の装備、難易度補正を分離し、未確認の倍率を原作仕様として補わない。

BGMはユーザーが重視する再現項目。曲とミッションの対応、再生タイミング、ループ、音量・消音を調べる。原曲音源は未取得であり、[1-1のBGM方針](../missions/mission-1-1.md)に確認事項を残す。

1ミッション内の複数曲に対応する。曲の台帳と場面別の再生条件を分け、[BGMの観察表](../audio/bgm-mapping.md)から実際の対応を整理する。曲順・ランダム再生とイベントによる切り替えは、観察で区別する。
